# CloudCart — Architecture

CloudCart is intentionally small: one HTTP API surface, two DynamoDB tables, one processing queue with a DLQ, and five Lambda functions. The goal is a clear interview narrative about serverless, idempotency, and failure isolation rather than a large microservice mesh.

## POST /orders request flow

1. API Gateway routes `POST /orders` to the CreateOrder Lambda.
2. The handler validates `X-User-Id`, `Idempotency-Key`, and the line items, then computes `totalAmount`.
3. A new `orderId` is generated. A DynamoDB `TransactWriteItems` call attempts to insert both the order row (status `PAYMENT_PENDING`) and the idempotency row keyed by `SHA256(userId + ":" + idempotencyKey)`.
4. If the transaction succeeds, a compact message `{ orderId, userId, totalAmount, createdAt }` is sent to `OrderProcessingQueue`.
5. The API returns `201` with `idempotentReplay: false`, or an application error with a consistent JSON envelope.

## Idempotency flow

The idempotency table uses a conditional put (`attribute_not_exists(idempotencyKeyHash)`) inside the same transaction as the order insert. Concurrent duplicate requests contend on that condition: only one writer wins.

If the transaction is cancelled because the idempotency key already exists, the handler loads the idempotency record, fetches the original order, and returns `200` with `idempotentReplay: true`. Duplicate requests therefore do not create duplicate orders.

Idempotency records include `expiresAt` with DynamoDB TTL enabled so the portfolio stack does not accumulate unbounded metadata.

## SQS processing flow

1. SQS invokes the ProcessOrder Lambda with `batchSize: 1` to keep retry semantics easy to reason about.
2. The worker parses the JSON body, loads the order, and skips terminal states (`PAID`, `DELIVERED`, `CANCELLED`) without throwing so the message is acknowledged and removed from the queue.
3. For `PAYMENT_PENDING` orders, a small payment simulator runs. Outcomes are forced in tests via `PAYMENT_FORCE_RESULT`; in other environments `PAYMENT_FAILURE_RATE` biases random outcomes.
4. Success updates the order to `PAID`. Permanent failure sets `FAILED` with a `failureReason`. Retryable failure increments `attemptCount` and raises so the message returns to the queue after visibility timeout.

## Failure, retry, and DLQ flow

SQS redrive is configured with `maxReceiveCount: 3`. Retryable failures surface as Lambda errors, which causes SQS to retry until the receive threshold is exceeded, after which the payload is moved to the dead-letter queue for inspection.

CloudWatch log lines are structured JSON strings with an `event` field (for example `payment_failed`, `skipped_order`, `duplicate_idempotency_key`) so you can filter quickly while debugging.

## Cancellation rules

Cancellation is allowed only from `PAYMENT_PENDING` or `FAILED` via a conditional update. Paid or downstream fulfillment statuses return `409` so invalid transitions are visible to API clients.

## DynamoDB model

- **Orders table** — partition key `orderId`. GSI `userId-createdAt-index` supports listing a user’s orders sorted by `createdAt` descending at query time (`ScanIndexForward=false`).
- **Idempotency table** — partition key `idempotencyKeyHash`, TTL attribute `expiresAt`.

## Why keep the scope small

The project optimizes for a crisp story: idempotent writes, asynchronous work off the hot path, explicit retry and DLQ behavior, least-privilege IAM generated by CDK, and tests that run without an AWS account. A hiring conversation can stay anchored in trade-offs rather than cataloguing dozens of services.
